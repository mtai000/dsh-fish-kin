# 认知层设计：从"什么都会的宠物"到"规划如何去认知世界"

> 2026-10-31 补记：**内建 B 站已整体移除**（0.20.0）。本仓库不再含任何具体插件的实现；
> 世界一律通过 `perception.sources` 接入。下面 P1 里提到的 builtin 适配器已是历史。

> 2026-10-31 定案。B 站交给 `dsh_bili_scroll`，游戏交给 `dsh_play_cdda`。
> 本插件只做一件事：**决定她今天该去认识什么、批不批、记下来、再提炼成自己的判断**。
> 本文是开工前的契约；迁移清单在最后，按 P0→P5 走，每步可回滚。

---

## 1. 为什么要拆

现在这个插件会看 B 站、会评论、会私信、会看画面——但它真正的价值不在这些**能力**上，
而在**记忆、身份、成长、传承**上。能力越堆越多，带来三个症状：

1. **一个人扛所有外部世界的接口**。B 站接口一改（风控、签名、登录态），核心逻辑就要跟着动；
   每加一个世界（游戏、搜索、文件），核心再胖一圈。
2. **权限面失控**。她的工具面从 2 个涨到"2 个 + 一堆 B 站动作"，每条都可能被写进新的攻击面。
3. **职责说不清**。别人问"这插件是干嘛的"，答案是"养鱼 + 刷 B 站"，听起来像两个东西拼在一起。

拆开之后，本插件的定位只有一句话：

> **她负责"想认识什么"，世界负责"给她看到什么"。**

## 2. 职责边界

| 本插件做 | 本插件不做 |
| --- | --- |
| 记忆（事件流、折叠、身份、阶段/立场/疤） | 登录任何外部服务 |
| 认知规划（今天想看什么、为什么、预算多少） | 拉取/解析任何外部接口的数据格式 |
| 接入外部源（**只写配置**，`tools/link-source.mjs`） | 实现任何外部世界（B 站、CDDA 都是别人的插件） |
| 意图审批（要不要去、要不要说） | 执行动作（发评论、发私信、玩游戏） |
| 配额与风控（每天几次、谷时） | 平台风控规则（谁限流、谁要签名） |
| 记录（她看过了什么→`perceived`） | 平台数据的持久化（缓存、下载、封面） |
| 提炼（从感知到判断：utterance/amend） | 决定外部插件的 UI 长什么样 |

一句话：**外部世界通过"感知源（Source）"接进来，本插件只持有 Source 的清单和账本。**

## 3. 架构

```
                    ┌───────────────────────────────┐
                    │        dsh-fish-kin           │
                    │                               │
  身份/记忆/成长 ◄──┤  core: store identity growth  │
  传承/族谱     ◄──┤        lineage distill        │
                    │                               │
  审批/配额     ◄──┤  intent: planner approvals    │
                    │          quota schedule       │
                    │                               │
                    │  perception: registry         │
                    │    sources/bili.js  ──┐       │
                    │    sources/cdda.js  ──┤       │
                    └───────────────────────┼───────┘
                                            │ 只读调用 + 执行请求
                            ┌───────────────┴───────────────┐
                            │  dsh_bili_scroll              │
                            │  （B 站：搜索/热评/画面/投递） │
                            ├───────────────────────────────┤
                            │  dsh_play_cdda                │

                            └───────────────────────────────┘
```

关键：**core 不认识 B 站，也不认识 CDDA**。core 只认识 `Source` 接口。

## 4. Source（感知源）接口

每个世界给本插件一份清单：

```js
// 由外部插件提供（或由本插件写一份 adapter 去对接它暴露的工具）
{
  id: 'bili',
  title: '看 B 站',
  tools: {
    read: ['bili_search', 'bili_hot'],
    act:  ['bili_comment', 'bili_reply', 'bili_dm'],   // 需要意图审批
  },
  budget: { perDay: 3 },        // 本插件负责计数
  offpeak: ['noon', 'night'],   // 本插件负责时段
  summaryMax: 120,              // 回给她的摘要上限（token 预算）
}
```

**契约只有三条**：

1. **只读工具直接调**：她可以随时用 `read` 类工具（不消耗配额、不走审批）。
2. **执行类工具必须先过意图审批**：她写一张"我想做 X"的单子 → 你批 → 再调用 `act` 工具。
   审批的执行由外部插件自己做（它更清楚自己的风控），本插件只负责"批没批"。
3. **返回必须带摘要与引用**：`{ ok, summary, ref }`。`summary` 进 `perceived` 事件；
   `ref` 是原文/详情的位置（URL、存档 id），只留指针，不留全文。

## 5. 认知循环

```
① 规划（planner）
   看什么：她的 interests + 上次 perceived 的空缺 + 阶段
   产出：intent 事件 { goal, source, why, budget }
        ↓
② 审批（approvals）
   propose：立一张单等你点头；auto：你已在设置里同意
        ↓
③ 执行（外部插件）
   她调用该 source 的 act 工具；本插件不碰网络
        ↓
④ 记录（perceived）
   { source, subject, summary ≤120字, ref, at }
        ↓
⑤ 提炼（她的判断）
   她可以自己写 utterance / amend —— 这一步不许由插件代写
        ↓
⑥ 影响下一次规划（feedback）
   看过的方向加权；没看完的留成"想继续"的 intent
```

**红线**：④→⑤ 不许自动摘要成判断。`perceived` 只是"她看到了什么"，
"她怎么想"只能由她自己的 `fish_commit` 写。

## 6. 事件模型变更

现有七种：`seed / said / amend / refuse / diary / note / woke`。

新增两种（只追加，兼容老档）：

```jsonc
// 她想认识什么（规划）
{"kind":"intent","body":"想弄明白：AI 手绘工作流到底解决了什么","src":"system","day":12,
 "meta":{"source":"bili","goal":"learn","budget":{"mins":10}}}

// 她看到了什么（感知，来自外部插件）
{"kind":"perceived","body":"AI 手绘工作流：作者用三步把草图变成线稿","src":"system","day":12,
 "meta":{"source":"bili","subject":"BV1xx","ref":"https://b23.tv/BV1xx","lexicon":3}}
```

- 两种都**不**进身份段的"你说过的话"，只进"最近看到 / 最近想弄明白"两小节（有上限、会折叠）。
- 旧档没有这两种，`derive()` 需要容错（缺 meta 就当空）。

## 7. 工具面变化

| 版本 | 她的工具 |
| --- | --- |
| 0.14（现在） | `fish_commit` + `fish_bili`（+ `read_image`） |
| 拆分后 | `fish_commit` + **每个已启用 source 的 `read` 工具** + `read_image`（只有看图源启用时） |

- `act` 工具**不在**她的工具面里：她的"行动"是交单子，由你批准后由本插件代调（或由带权限的外部代理调用）。
- 已禁用 source 的工具**一律不进**工具面——这就是"拆出去"的实际效果。

## 8. 配置形态

```jsonc
{
  "style": { "preset": "cute", "text": "" },
  "wake": { "enabled": true, "perDay": 2, "window": ["09:00","23:00"] },
  "perception": {
    "sources": {
      "bili": { "enabled": false, "adapter": "external", "tools": { "read": ["bili_search","bili_hot"], "act": ["bili_comment"] },
                "budget": { "perDay": 3 }, "offpeak": ["noon","night"] },
      "cdda": { "enabled": false, "adapter": "external", "tools": { "read": ["cdda_observe"], "act": ["cdda_move"] },
                "budget": { "perDay": 1 }, "offpeak": ["night"] }
    },
    "interests": ["人工智能", "独立游戏"],
    "goalSources": ["bili","cdda"]        // 规划时按这个顺序问"今天去哪"
  }
}
```

旧的 `bili.*` 配置**保留读取**（迁移期），但只在 `perception.sources.bili.adapter === "builtin"` 时生效；
默认 `external`，即内建 B 站代码休眠。

## 9. 迁移清单

每步都能单独发布、单独回滚；括号里是验收标准。

### P0 · 抽出感知层骨架（不改行为）
- 新增 `lib/perception/{registry.js, planner.js, sources/index.js}`。
- `registry` 只管：已启用 source、它们的工具清单、预算与时段。
- `planner` 产 `intent` 事件（先只写事件，不驱动任何执行）。
- 验收：现有 299 条测试全绿；`intent` 能落盘且不进身份段正文。

### P1 · 内建 B 站改成 source adapter（默认不挂）✅ 0.16.0
- `lib/fish/bili|login|qr|video|offpeak|report|owner` → `lib/perception/sources/bili/`（原样搬，不改逻辑）。
- 旧的 `fish_bili` 工具保留，但注册条件改成 `adapter === "builtin"`（**默认 external = 不挂**）；身份段也不再提它。
- 验收：`adapter=builtin` 时测试与 0.14 全等（同一套 case 迁移过去）；`adapter=external` 时 `fish_bili` 不出现。

### P2 · 新事件类型进派生与界面 ✅ 0.17.0
- `derive/identity/observe/report` 认识 `intent` / `perceived`（两小节 + 折叠上限）。
- 验收：身份段出现"最近想弄明白""最近看到"，条数有上限；观测台能列出。

### P3 · 默认下线内建 B 站，接外部 source ✅ 0.18.0
- 默认 `sources.bili = { enabled: true, adapter: "external", tools: {...} }`，工具名以 dsh_bili_scroll 实际暴露的为准（先做成配置可改）。
- 她的工具面：`fish_commit` + `fish_ask` + 外部 `read`/`act` 工具；`fish_bili` 消失。
- 审批单类型从 `bili-comment` 泛化成 `source-act`（带 source id 与工具名）。
- **执行方式（0.18.0 实测后的定案）**：宿主没有稳定的"代调用工具"入口，所以不代调。
  批准 `source-act` = 发一张 **30 分钟、一次有效** 的通行证；她调用 `act` 工具时守卫检查通行证，
  有就放行一次并作废，没有就让她先用 `fish_ask` 立单。执行权始终在对方插件手里。
- 验收：未装 dsh_bili_scroll 时一切正常（source 报"没接上"）；装了之后 `read` 工具可见、`act` 走审批。

### P4 · 不写任何 source 适配器（✅ 修正）
- **P4 原方案写错了**：给 CDDA 写 `sources/cdda.js` 等于在解耦之后又把耦合塞回来。
  玩法与感知都在 `dsh_play_cdda` 里；本仓库只写**配置**，不写那个插件的代码。
- 交付：`tools/link-source.mjs`——把任意插件接成感知源（只写 `perception.sources`，不碰别的配置）。
- 验收：接入 bili 与 cdda 都只是同一行命令，本仓库不新增任何 cdda 相关文件。

### P5 · 文档与界面收尾
- README/视频稿/设置页：B 站卡片搬进"感知源"分组；设置页只显示已启用的 source。
- 验收：文档里没有"本插件会刷 B 站"的表述。

## 10. 测试策略

- **core 不测网络**：所有外部调用走注入的假 registry（`{ read(){...}, act(){...} }`）。
- **每个 source 一套契约测试**：`read` 返回 `{ok,summary,ref}`；缺 `summary` 视为契约违约（明确报错，不静默）。
- **审批泛化测试**：`source-act` 单批准后调用对应工具、驳回后不调用。
- 迁移期间保留 0.14 的 `test/bili.test.mjs` 等，作为 `adapter=builtin` 的回归集。

## 11. 明确不做

- 不做"通用 agent 调度器"：只调度已声明的 source，不做任意工具编排。
- 不替外部插件做执行层的审批（它更懂自己的风控）。
- 不把感知内容自动写成她的判断（④→⑤ 必须她本人写）。
- 不保留两套并行的 B 站实现超过两个版本（`builtin` 在 0.16 之后删除）。

## 12. 风险

| 风险 | 处理 |
| --- | --- |
| 外部插件工具名/返回形状不稳定 | 工具名、摘要字段全部进配置；契约违约时明确报"没接上"，不装成功 |
| 拆完她"什么都不会" | `builtin` adapter 保留两个版本做回退；关闭 source 只影响能力，不影响记忆/传承 |
| 审批重复（我们批一次、对方再批一次） | 约定：**意图**归我们，**执行**归对方；对方若也审批，就是两道，接受 |
| token 变贵（摘要要点进身份） | `summaryMax` 默认 120 字、两小节各 3 条、折叠 |
